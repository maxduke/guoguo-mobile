# 果果：产品体验与全新重构建议

日期：2026-10-07。按新 App 设计，不要求旧安装数据迁移。

评审阶段阅读了主要页面、搜索与续播路径、下载管理、状态及存储边界、播放与投屏协调，并查看仓库布局预览和相关测试。结论来自源码与静态预览，不是本轮真机测试。预览使用合成内容，部分图片的站源入口早于当前源码；站源与交互行为以源码为准。

后续按用户要求先实施问题修复与维护性优化：修正续播／历史的真实集号展示及追剧续播的来源筛选，去除未变化资料与已读集集合引起的记录写入，并统一资料比较与观看记录资料更新。当前行为见 [状态与页面更新边界](app-state.md)；本文其他产品重构建议仍是规划，不代表已经实现。

## 1. 产品方向

建议把果果定位为：**打开就能接着看，也能快速找到下一部剧的独立短剧 App。**

保留暖白／墨绿、深浅主题、无账号使用、本机记录、离线下载、手机／平板适配。当前已经有记录与目录分区存储、局部状态通知、固定播放按钮、选集定位、下载批量管理、独立播放／投屏会话；这些是值得继续使用的基础。

最需要改变的是入口和主流程：

- 当前找剧主要围绕站源目录展开，用户先选站源，再理解该站的搜索、分类和榜单能力。
- 推荐、榜单、剧库分别承担找剧功能，推荐还要进入独立页面。
- 续播卡片可以直接开播，但收藏／历史的普通列表条目仍先进入详情页。
- 下载页把任务状态、空间管理、来源、排序和多选集中在同一首屏。
- 播放页还承担大量本地播放、恢复、系统生命周期与投屏的协调。

不要用功能数量评价重构成果。优先评价：找剧步骤是否减少、续播是否准确、切集是否稳定、失败后是否知道下一步。

## 2. 优先级

| 优先级 | 工作 | 用户收益 | 工程成本 |
| --- | --- | --- | --- |
| P0 | 准确续播、明确播完状态、展示原始集号 | 回来即看，减少重复点选与错误集号 | 中 |
| P0 | 收拢播放协调，统一故障与投屏交接体验 | 连播和手机／电视切换更可预测 | 高 |
| P0 | 缓存和记录先呈现，下载恢复不阻塞首页 | 启动就能看到自己的内容 | 中 |
| P1 | 发现页合并推荐、榜单、分类入口 | 减少找剧跳转，首屏直接展示内容 | 中 |
| P1 | 独立搜索页与有预算的多站搜索 | 不必反复切站重新输入 | 高 |
| P1 | 常用站源与能力说明 | 十六站选择更轻，少走不可用路径 | 中 |
| P1 | 下载改用剧卡片，默认收起分集，存储管理独立 | 少筛选、易续看、易清理 | 中 |
| P1 | 紧凑详情、手势简化、无障碍与平板导航 | 核心操作更容易发现和触达 | 中 |
| P2 | 有类型的站源接口、按实体存储、统一缓存生命周期 | 降低维护成本与大记录量下的写入负担 | 高 |
| P2 | 移除重复界面、未使用兼容路径和开发入口负担 | 让产品与代码都更聚焦 | 低至中 |

成本为相对估计，不是工期承诺。

## 3. 推荐的新导航

| 入口 | 默认内容 | 次级入口 |
| --- | --- | --- |
| 发现 | 搜索、继续观看、精选内容、热门与分类 | 完整榜单、按站浏览、站源管理 |
| 追剧 | 继续观看、最近更新、收藏列表 | 历史、筛选、追剧提醒设置 |
| 下载 | 按剧聚合的离线内容及活跃任务摘要 | 单剧分集、任务问题、空间管理 |
| 设置 | 外观、播放、网络、存储、备份 | 关于、问题诊断、可选高级工具 |

设置仍用顶部入口，维持三个主标签。保留按站浏览，但让它成为主动选择的浏览方式。

发现页只请求当前选定或常用来源的必要内容，不在启动时自动扫描十六站。公共推荐、真实榜单、目录排序继续明确区分。

## 4. 找剧：先展示内容，再提供工具

### 4.1 合并发现、推荐与榜单入口

**当前证据：** [home_page.dart](../lib/ui/home_page.dart) 的 `_discover`、推荐入口卡片和 `_library`；[recommendations_page.dart](../lib/ui/recommendations_page.dart)；[rankings_page.dart](../lib/ui/rankings_page.dart)。

把“今天，看点什么”的入口卡片改成直接展示内容的横向推荐区；首页展示一小组热门内容，“查看全部”进入完整榜单。分类提供少数常用标签，其余放进筛选面板。

压缩品牌标语、大标题、排序与分类的多层纵向排列。保留视觉留白，但让第一屏更快出现可点的剧集。加载数量和“已加载数量不代表全站总量”移到列表末尾或数据说明处，不能把已加载目录数量当作全站总数。

推荐页目前以页面内的空 `rows` 开始，离线直接报错；获取的条目虽然合并到目录，却没有保存可恢复的推荐列表。建议内容仓库保存每个推荐栏目／榜单的顺序与更新时间，重进页面先显示已有内容，再刷新。不要把整个缓存剧库冒充上次推荐结果。

### 4.2 搜索成为独立完整流程

**当前证据：** [home_page.dart](../lib/ui/home_page.dart) 的 `_queryChanged` 与 `_submit`：输入先过滤已加载条目，提交才联网搜索；站源切换会清空搜索。黄豆没有联网搜索，黄果联网搜索只覆盖 AI 子源。

建议点击搜索框进入专门页面，保留最近搜索、清空、返回后恢复结果和滚动位置。联网时，输入完成后只提供联想，提交后执行明确的搜索；离线明确标注搜索缓存。不要让一组临时本地匹配看起来像最终搜索结果。

默认搜索用户启用的常用站源，并允许限定单站。多站搜索必须：

- 限制并发、总时限和每站页数；优先返回已经成功的结果。
- 取消旧查询，保留当前已有的输入法组合态保护、请求代次校验和限流。
- 说明哪些来源还在搜索、失败或不支持；部分失败不覆盖已成功结果。
- 先按来源展示，不按同名自动合并作品和观看进度。名字相同可能是不同版本、不同集数或不同作品。
- 对黄果标明“AI 剧”，对黄豆明确“仅缓存”，而不是承诺全部十六站同等搜索能力。

多站搜索是新增能力，需要新测试与网络成本评估；仅做统一搜索页面也能先改善体验。

### 4.3 站源管理减少选择负担

**当前证据：** [models.dart](../lib/domain/models.dart) 定义十六站；[source_selector.dart](../lib/ui/source_selector.dart) 已有可搜索网格，当前直接展示全部站源，没有常用／隐藏或健康状态。

保留现有网格作为“更多站源”，增加常用、最近使用、隐藏来源。默认常用数量可以先控制在 3–5 个，再依据覆盖面和实际使用调整。首屏只需显示当前来源或搜索范围。

站源能力由明确的描述对象提供：搜索范围、分类、真实榜单／目录、VIP、下载、媒体准备与投屏限制。健康状态只能来自实际请求结果及时间戳；没有近期验证的来源显示“未验证”，不能凭是否能返回目录标成播放正常。

优先隐藏不常用来源。只有确认低价值、长期不可用且无独特内容后，才删除适配器；暂时请求失败不足以决定永久删除。

## 5. 追剧：把续播作为主要动作

**当前证据：** [home_page.dart](../lib/ui/home_page.dart) 的 `_personal` 仅顶部续播卡片直接播放，列表条目通过 `_open` 进入详情；[record_store.dart](../lib/data/record_store.dart) 的 `recent` 只按观看时间排序。

建议：

- 最近观看展示少量可直接续播的条目，而不是只突出最近一部。每条有“继续第 N 集”主动作和“详情”次动作。
- 收藏但未看过的剧显示“开始观看”；追到最新但未完结显示“等待更新”；确认整部看完后显示“已看完”，从继续观看区移出，记录留在历史。
- 自动跳到下一集只使用可靠的播完记录；手动暂停在结尾附近不能仅凭百分比被当成已经看完。
- “有更新”用于排序或轻量筛选，不额外引入一整套复杂的想看／在看／已看管理。
- 历史移到次级入口，支持按剧批量删除；删除记录与视频保持分开。
- 来源筛选的作用范围一致。当前追剧列表先筛来源，顶部续播仍使用全局 `recent.first`；若保留全局续播，须在版面上明确它不受下方筛选影响。

**集号需要单独修正。** 续播和历史文案用 `episodeIndex + 1`，详情和播放器用 `Episode.number`。仓库测试已有原始集号为 2、4、6 等的样本，数组位置与展示集号并不等价。新记录保存 `episodeId`、真实集号和位置；数组索引只用于当前队列，不作为用户集号。

把收藏按钮统一为容易理解的追剧动作，新集检查成为追剧设置。按标题匹配的“同系列新季”保留独立可选项，不默认开启，也不承诺系统通知；当前实现是应用内检查与提示。

## 6. 详情与播放：主动作简单，异常有出口

### 6.1 详情首屏更紧凑

**当前证据：** [detail_page.dart](../lib/ui/detail_page.dart) 已有固定底部播放／下载、分页选集、当前集定位和原始集号。

继续保留固定主按钮。把封面、标题、集数、状态和追剧按钮收进紧凑摘要区；简介默认少量行，展开后看完整内容。同系列放在选集之后或次级页，避免先滚过系列工具才能选集。

不要只靠长按分集来下载。已有下载范围面板适合作为明确入口，分集长按只提供快捷操作菜单或作为可选捷径。“定位当前”“跳集”保留，避免重做已解决的长列表定位问题。

### 6.2 手势保留高频动作，删除重叠动作

**当前证据：** [player_gestures.dart](../lib/ui/player_gestures.dart) 同时提供横滑跳进度、长按 2 倍速、长按再横滑跳进度；[player_sheets.dart](../lib/ui/player_sheets.dart) 需要长段文字解释。

建议保留单击显隐、上下切集、横滑预览并在松手后跳转、长按临时加速。去掉“长按后横滑调进度”，与普通横滑功能重复，也容易把加速误变成跳转。只在首次需要时给一个短提示，不反复展示教程。

全屏、投屏和 PiP 按实际可用能力提供明确入口。读屏和手部操作不便时，播放、暂停、上一集／下一集必须可通过控件操作。当前已经有 tooltip 和部分 Semantics，下一步要验证整条读屏操作路径；控件 3 秒自动隐藏的规则应考虑辅助功能使用状态。

手势建议与 [Apple 手势指导](https://developer.apple.com/design/human-interface-guidelines/gestures) 的一致性原则一致；可操作性验收参考 [Flutter 无障碍指导](https://docs.flutter.dev/ui/accessibility)。

### 6.3 等待与错误提供有意义的选择

当前加载页已经显示准备阶段，也保持返回与选集可用，不应重复开发这一点。下一步把超时、离线、授权、来源故障、空间不足、解码失败分成用户能理解的状态，分别提供重试、换集、播放本地或释放空间。

[player_page.dart](../lib/ui/player_page.dart) 在错误区域显示最多 600 字符的 `_error`；其他页面也有直接展示异常字符串的路径。统一转换为简短说明，技术详情保留到可复制诊断中。不能把所有故障都引导为重复点击“重试”，也不能自动切到同名的另一站作品。

### 6.4 投屏统一入口与结果

**当前证据：** AirPlay 在播放器顶部；Google Cast／DLNA 通过“更多”进入。[cast_sheet.dart](../lib/ui/cast_sheet.dart) 明确提示保持前台、离开播放页结束投屏。

统一为“投屏”入口，面板包含系统 AirPlay 选项及发现的其他设备。界面统一连接中、已连接、失败、返回手机的状态；AirPlay 仍使用系统路由选择，不强求把所有协议设备塞进同一个原生列表。

连接后展示设备名、播放状态和可确认进度。已有的“收起面板继续投屏”“结束后交回手机进度”继续保留。可以进一步让会话由应用持有，离开播放页后通过小型控制条返回；中转仍须前台时继续明确告知，不将页面解耦误写成后台播放能力。

控制能力按协议和设备实现：AirPlay 已有独立队列连播；Cast／DLNA 的选集、连播和重连仍要单独建设。未知电视进度不能伪造。移交失败时保持单一播放端，不能同时播放手机和电视。

## 7. 下载：默认是离线剧库，任务细节按需展开

**当前证据：** [downloads_page.dart](../lib/ui/downloads_page.dart) 首屏同时有“下载任务／按剧空间”、来源、五种状态、排序和多选；分集列表默认展开。

现有下载已经按剧归类，建议在此基础上默认收起分集，以剧卡片显示封面、已下载／总集数、占用、继续离线观看、活跃任务摘要。点进单部剧看分集；正在下载或失败的剧显示进度／重试，不把所有已完成分集铺满首页。

- 任务查看简化为“进行中／已完成”，失败和暂停在进行中按状态显示；需要批量处理时再展开状态筛选。
- “管理空间”作为独立入口，继续提供大小排序、按剧多选与删除确认，删除前显示释放量。
- 来源和排序放筛选面板；批量暂停／恢复／重试保留在选中后的操作栏。
- 下载范围面板保留“接下来 10 集”“整部下载”；有可靠大小时展示估算，未知则显示未知，已有下载不计入新增需求。
- 下载完成与“正在整理视频”明确区分，后者不能提前宣传成可离线观看。
- 离线队列只播放已有下载。若下载为第 1、3、5 集，切集时提示下一集未下载，并允许明确选择跳到第 3 集，避免把离线队列索引当成连续正片。

下载列表当前在每次下载通知后重做筛选、分组和排序。可把结构变化与单集进度分开通知，缓存分组并局部更新进度；先用长队列分析帧耗时，不凭源码断言现有页面一定卡顿。

## 8. 设置、平板与视觉

**设置：** 合并为外观、播放与网络、存储、备份、关于。记录备份有未来换机价值，应保留；“不迁移旧安装”不意味着新 App 不需要导出自己的记录。JSON／XZ 剧库互通移至高级工具，若用户不再需要桌面互通，可删除对应 UI 与交换模块。保留诊断采集，把技术列表和实验开关收进问题反馈／开发入口。

**存储：** 当前设置主要提供下载占用和封面清理。新版本统一展示完整下载、下载临时文件、播放临时文件、封面、目录缓存各自的统计范围；避免重复统计。目录／封面可重建，清理不能删除收藏或已下载视频；正在播放和投屏的资源不能被缓存清理释放。

**平板：** 当前首页仍使用底部导航，主要靠增加列数和 900 宽度的分支；详情已有分栏。建议按实际窗口宽度选择底栏或侧栏，较宽时支持列表与详情并排，播放器选集用侧面板。iPad 分屏也要能保留当前站源、搜索、滚动位置及播放会话。参考 [Flutter 自适应设计指导](https://docs.flutter.dev/ui/adaptive-responsive/general)，断点应依据可用窗口空间制定。

**视觉：** 保留现有色系，统一海报比例、标题行数、按钮与卡片间距、状态徽标。为长标题和大字体调整卡片高度；缺封面时保留已有回退样式。对收藏、加入下载、选集提供即时明确反馈，谨慎使用短触觉反馈。海报展示真实内容后再评估视觉密度，不把合成占位图当成最终观感。

## 9. 工程重构：保留底层能力，重新整理职责

### 9.1 先释放启动路径

[main.dart](../lib/main.dart) 的 `_initialize` 在展示首页前顺序等待记录载入、核心初始化、下载初始化和网络检查；下载初始化还包含清理与恢复。

新启动流程先确定本地数据和展示主题，尽快呈现缓存与记录；站源核心、下载恢复和网络状态作为独立就绪状态加载。未就绪功能给出局部状态并允许重试，不能让一个子系统阻止进入整个 App。分阶段初始化必须处理取消、重复重试、插件依赖和资源释放，不能仅把所有 `await` 换成未等待任务。

### 9.2 继续提取播放协调，不合并协议内核

[player_page.dart](../lib/ui/player_page.dart) 已使用 PlaybackSession、PlaybackLifecycle、恢复控制器和独立 AirPlay／CastSession，但页面仍安装播放源、处理原生事件、协调互斥、持久化进度并交接播放端。

建议由应用层的播放协调器接收播放／暂停／选集／投屏命令，管理当前作品、队列和播放意图；本地播放器、AirPlay 队列、Cast／DLNA 使用各自的适配器。UI 只显示状态和发送命令。设备能力、取消代次、旧资源保留、失败预算和释放顺序仍是必须保留的行为。

这与 [Flutter 架构建议](https://docs.flutter.dev/app-architecture/recommendations) 中 UI 与数据职责分离的方向一致。现有 ChangeNotifier／Listenable 可以继续用，换状态管理框架不是主要收益。

### 9.3 站源接口有类型，领域模型保持稳定

[provider_client.dart](../lib/platform/provider_client.dart) 用方法名和动态 Map 调用，Go 在 [mobile_api.go](../native/core/internal/app/mobile_api.go) 分派请求；`Episode.raw` 保存上游原始字段并参与播放与下载。

在原生桥接外包一层明确的目录、搜索、详情、播放与下载接口，集中解析和校验响应。领域分集保留 ID、真实集号、标题、授权等稳定字段；解析所需的站源专属数据放在适配器或不透明引用中。先验证每个保留站源的真实契约，再删原始字段，避免漏掉签名播放或下载凭据所需资料。

继续使用设备内 Go 核心及独立运行边界。没有证据表明把站源逻辑全部改写成 Dart 或切换纯原生 UI 能带来与成本相称的收益。

### 9.4 数据以实体更新，缓存有独立预算

现有记录／目录分文件和写入串行化应保留其可靠性语义。剩余问题是 [app_store.dart](../lib/data/app_store.dart) 的记录快照还包含偏好、目录设置、诊断、收藏、完整历史和已读集基准；改一个设置也经过记录快照写入。

全新版建议评估用 SQLite 按剧集、观看记录、收藏、分集与任务实体保存，偏好独立保存，更新单条进度不重写整份记录。数据库是工程取舍，不是已经测出的性能修复；应对照真实记录规模、启动耗时和写入次数再锁定。

“检查追剧更新”“资料刷新后同步记录”由应用服务协调，减少 CatalogStore 与 RecordStore 的双向调用。新存储仍要支持原子提交、失败恢复、备份预览和排队中的并发修改。

缓存统一定义容量／时间预算，但按目录、封面、搜索、播放准备和下载分区管理。完整下载不是缓存，当前播放资源有持有关系。不要用一个简单“清理全部临时目录”实现全局清理。

## 10. 精简与删除清单

| 项目 | 建议 | 条件或代价 |
| --- | --- | --- |
| 独立推荐页作为必经入口 | 合并进发现页；完整栏目可继续二级浏览 | 保留来源及推荐顺序 |
| 首屏品牌标语、重复大标题、常驻技术解释 | 压缩或移入具体状态的说明 | 流量、VIP、投屏前台等必要信息仍在相关操作时显示 |
| 多处刷新、重复排序和筛选入口 | 每个页面保留一套主要方式 | 错误状态保留明确重试 |
| 长按再横滑跳进度 | 删除 | 普通横滑和长按加速继续保留 |
| 下载分集默认全部展开 | 改成默认按剧聚合 | 单剧详情和批量操作可达 |
| JSON／XZ 剧库互通 | 移到高级；无使用需求时删除 | 会失去桌面／其他应用交换能力 |
| 普通设置中的实验开关和完整技术诊断 | 收进开发／支持入口 | 保留内部测量与错误信息 |
| 长期低价值站源 | 先隐藏，证据充分后删除适配器 | 可能失去独特内容；不可仅凭一次失败决定 |
| 旧版本迁移路径 | 全新版不建设；确认残留后删除 | 当前 README 已按新安装维护、备份只收 v2，不能重复计算已完成的精简 |
| 外部交换编码别名、桥接版本检查、媒体兼容回退 | 依据仍支持的契约决定 | 它们可能是当前外部兼容性，不能当作旧用户迁移一并删掉 |
| 提前开播实验的第二套准备路径 | 根据真机对照决定保留一种主策略或必要回退 | 直接删除可能增加加密剧首次等待；保留则有临时媒体和回退复杂度 |
| 历史实施文档 | 可归档，维护一份当前产品规格 | 不影响 App 运行性能，不能当作包体优化 |

不新增账号、社交、弹幕、复杂 AI 推荐、自建服务器等主流程之外的系统。当前最值得投入的仍是找剧、准确续播、稳定连播与离线观看。

## 11. 实施与验收

建议分四轮，每轮都能交付完整流程：

1. **续播和播放基础：** 统一真实集号与续播动作，定义播完状态；整理播放协调、异常、投屏入口；启动分阶段就绪。
2. **找剧：** 发现页重排、独立搜索、常用站源和内容缓存；多站搜索按预算补上。
3. **离线与大屏：** 下载按剧聚合、空间管理、紧凑详情、平板导航和无障碍。
4. **数据与减法：** 类型接口、实体存储与缓存预算；根据使用与兼容证据删除来源、交换模块或实验路径。

验收重点：

- 有观看记录的剧，一次明确的续播动作进入正确分集和位置；原始集号非连续时文案仍准确。
- 收藏、历史、提醒、下载列表的来源筛选具有一致语义。
- 搜索部分来源失败仍可浏览成功结果；输入法组合态、清空、切换范围、退出后的迟到响应不污染页面。
- 已缓存内容重进后立即可见，刷新失败保留内容与真实更新时间。
- 飞行模式下，从下载进入整条离线队列不发起在线媒体播放；缺集有明确提示。
- 播放、暂停、切集、后台／PiP、投屏与回手机的组合流程维持单一播放端、准确进度和资源释放。
- 下载传输、前台整理、暂停原因和失败状态明确；空间不足与批量操作部分失败保留可恢复任务。
- iPhone 小屏、长标题、大字体、VoiceOver、iPad 横竖屏和分屏都能操作完整主流程。

性能基线应固定真机、站源样本、网络和缓存条件，记录冷启动到内容可见、点击到可见画面及音频、续播等待、切集等待、卡顿、内存、磁盘写入和耗电，区分典型值与尾部情况。当前诊断以“进度首次前进”计时，不等同于首帧，也不能用 Linux 合成媒体的耗时宣称真机秒开。

没有本轮真机对照之前，不承诺换播放器、删除渐进准备或引入数据库会提升具体百分比。
