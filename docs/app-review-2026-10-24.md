## 优先修复

### F1．红果“加载更多”没有读取官网下一页

**优先级：高。证据：真实接口抽查 + 源码。**

- `native/core/internal/app/provider_hongguo_search.go:291` 的 `fetchHongguoSearchPage` 固定请求 `page=1`，`hasMore`、`totalPages` 只转为 `Limited`。
- `native/core/internal/app/mobile_search_seasons.go:118` 的首屏基于已有结果建立补季游标；`:142` 之后的续页只调用名称检索来探测后续季，没有请求官网 JSON 的第二页。
- `lib/ui/catalog_search_controller.dart:183` 仍可能显示“上游未提供完整分页”，已不符合当前接口能力。

实测搜索“大佬”：App 第一页 18 条，加载第二页仍为 18 个唯一 ID，且仍提示有更多。独立读取官网 JSON 第一、第二页，各返回 10 条，第二页 ID 与第一页不同；当时官网报告 221 条、23 页。数量会随站点更新，问题依据是第二页存在而当前续搜不读取它。

**影响**：泛关键词搜索漏掉后续作品；反复加载可能只得到相同集合。上一版修复了搜索入口，尚未把新接口的真实分页接入原来的补季续页机制。

**建议**：在现有不可变续页快照中分别记录官网页号/是否还有下一页与补季状态，按需读取下一页并按站源和作品 ID 合并。保留取消、重放、有效期、单次请求和结果数量预算，不一次拉完所有页面。同步修正提示。

**必要回归**：普通词返回互不重复的官网第二页；普通分页与补季同时存在；某一分支失败后保留结果并重试；查询变更/取消；重复使用相同续页令牌；磁盘缓存恢复后重新取得联网游标。现有测试主要覆盖官网第一页和补季续页。

### F2．首次入队没有与暂停、删除共用操作边界

**优先级：高。证据：源码确认，需补受控 Flutter 回归。**

`lib/data/download_store.dart:633` 先将新条目加入清单并保存，`:642` 通知页面，再于 `:643` 逐个等待原生资源入队。这里的 `_enqueuing` 只防止同一分集重复创建。暂停 `:688` 和删除 `:888` 使用另一套 `_removing`，首次入队循环不检查该集合、条目是否仍存在、暂停意图或操作代次。

可形成的交错是：

1. 分片较多的下载开始提交，条目已在下载页可见。
2. 一个 `driver.enqueue` 尚未完成时，用户暂停或删除该条目。
3. 暂停/删除处理当前已存在的原生任务并返回；删除还会清理目录和清单。
4. 旧入队 Future 返回，原循环继续提交其余任务。

详情页批量下载期间允许返回；当前分集的异步提交仍可继续，随后下载页可操作该条目。因此不能只依赖详情页的忙碌按钮防止交错。大量 HLS 分片会扩大这个窗口。具体设备复现频率仍取决于原生队列调度。

**影响**：暂停后仍有新任务加入；删除后可能残留后台传输及无法在当前清单管理的文件。现有“删除与暂停互斥”测试没有覆盖首次入队与这些操作的重叠。

**建议**：同一条目的首次提交、暂停、重试、删除统一协调；每个异步提交后检查取消/代次及条目归属。删除需使旧提交失效、等待在途提交结束，再完成原生取消与文件清理。不同条目保持独立，不引入覆盖所有下载的全局长锁。

**必要回归**：FakeDriver 用 Completer 挡住一个提交，期间分别暂停、删除、关闭 Store，再放行；断言不会迟到加入新任务、不会留下已删除条目的原生任务。覆盖提交失败、取消失败与清单写失败。

### F3．聚合目录锁覆盖网络 IO，等待锁不服从请求超时

**优先级：中。证据：源码 + Go 受控复现。**

`native/core/internal/app/mobile_api.go:214` 的黄果分支，以及 `:233` 的红果/黄豆分支共用 `catalogMu`，持锁执行远程请求和缓存文件写入。`Call` 在 `:106` 创建期限，但 `sync.Mutex.Lock()` 本身不响应 context。

受控用例锁住 `catalogMu`，调用真实 `Call`，传 `timeoutMs=100`；约 300 ms 后才释放锁。调用实际在 **302 ms** 返回 `context deadline exceeded`。因此期限到达时不能退出等待；线上耗时取决于前一个请求持锁多久。原生桥接支持并发派发，这个串行化发生在核心内部。

**影响**：切换站源后，新目录可能被旧的慢请求拖住；配置的超时不能约束排队时间。它主要影响共用锁的聚合目录，不等于十九站所有 API 都被锁住。

**建议**：按来源协调互相冲突的游标请求；跨来源远程获取不共用长锁。共享快照合并与同一缓存文件的写入继续串行保护，提交时检查请求代次和取消。队列等待也须支持期限/取消，不能直接删除现有锁造成丢更新或并发覆盖缓存文件。

**必要回归**：慢红果目录与黄果/黄豆并发；等待中超时/取消；同来源页序；两个来源完成顺序相反时缓存快照完整；写失败不破坏已取得内容。

### F4．已完成下载恢复时未排除空文件

**优先级：中。证据：源码确认。**

`lib/data/download_store.dart:402` 对 `ready` 条目只检查 `File.exists()`；`:1017` 的 `localFile` 同样只检查存在。初次整理 `:529` 会检查非空，但恢复/下拉校验及实际取本地路径没有沿用这一条件。

**触发**：清单标记已完成，而对应文件被截断为 0 字节。它会继续显示“已完成”并被返回给播放器；`retry` 又会因为 `ready` 直接返回。当前缺失/空输出测试针对初次整理，不覆盖已完成文件后来变空。

**建议**：显式校验和本地取用共同检查存在且长度大于零；无效时提供可重试状态并保留正确的清单错误反馈。进度通知路径不新增全盘检查，也不对每次刷新做整集解码/哈希。

**必要回归**：恢复 `ready=true` 清单后将文件截为空；下拉刷新与直接离线播放分别验证；与有效、缺失、不可读文件分开；恢复失败保留其他下载。

### F5．Wi-Fi 预缓冲策略在两处定义不一致

**优先级：中。证据：源码确认；实际计费网络未做设备验证。**

- `lib/main.dart:157` 将“确定为 Wi-Fi”定义为含 Wi-Fi 且不含 mobile，剧库预取使用该状态。
- `lib/ui/player_page.dart:907` 的下一集预缓冲只判断是否含 Wi-Fi；连接变化监听也使用这一较宽条件。
- 本地锁定版本 `connectivity_plus 7.0.0` 的 Android 实现对多种 transport 独立追加结果，接口允许多项，而非始终单值。

当能力列表同时包含 Wi-Fi 和 mobile、且未允许蜂窝预缓冲时，两条路径会得出相反结论。不能仅凭该列表断言实际流量一定走蜂窝，但当前策略不能一致表达严格的 Wi-Fi 限制。

**建议**：提取共用的网络允许条件，供首次检查、网络变化、剧库预取和下一集预缓冲使用。网络不确定时保守处理；不把链路类型当成成功联网的证明。

**必要回归**：Wi-Fi、mobile、混合、none、空列表及 VPN 组合，覆盖开始前和任务进行中、蜂窝开关与前后台。

## 值得补的恢复与交互能力

### R1．记录损坏后需要可执行的恢复入口

`FileStorage`/`AppStore.load` 保留损坏文件并报错是正确的数据保护。当前 `lib/main.dart:40` 捕获本地载入错误后只提供“检查空间、重试”；格式损坏时再次读取相同文件仍会失败，而设置页的备份导入入口尚不可达。

建议补启动恢复页：保留/导出故障文件、从既有 v2 备份预览恢复，以及明确确认后保留原文件并重新建立记录。继续复用现有备份校验与原子写入，不静默清空，也不连带删除下载。需覆盖损坏 JSON、结构不兼容、空间不足、用户取消与恢复写失败。

### R2．启动过渡页需要补暗色和小窗口验收

`lib/main.dart:71` 的 Bootstrap 固定浅色主题；错误页的居中 Column 没有滚动容器和 SafeArea。暗色模式冷启动会经过浅色 Flutter 页面；短横屏、大字体及多行错误提示存在布局溢出风险，后者本轮未渲染复现。主界面的短窗口提示区和播放器无障碍已有回归，不应据此推定 Bootstrap 也覆盖。

建议跟随系统暗色处理启动过渡，并为等待/错误/重试提供小窗口可滚动布局；先补 `640×320`、大字号、错误长文案和屏幕安全区域的 widget 测试，再做设备验收。

### R3．保存失败告警需要独立的“重试保存”动作

`lib/ui/home_page.dart:254` 对记录/偏好保存失败只显示告警，没有像站源初始化失败那样提供重试按钮。磁盘恢复可写后，目前通常依赖下一次操作或观看进度保存触发重试；再次点击收藏、主题等原操作可能改变用户想保留的状态。

建议复用 `AppStore.persist(cache: false)`，提供明确的保存重试和进行中状态，失败继续保留告警；不通过重新联网或切换原设置来重试。记录写入、缓存写入和下载清单仍使用各自的错误与队列。此项为恢复体验改进，现有告警和内存状态保留机制仍有价值。

| Go `MobileClient.Call` | 随功能修复逐步提取域处理函数，优先解决锁和续页契约。 | 原生桥接协议、错误脱敏、搜索/代理/预取上限及明确 Close 归属。 |
| 播放器/数据库/状态框架 | 当前继续使用现有实现。 | 新框架不能代替真实画面、恢复耐久性或资源生命周期的证明；有设备测量和具体瓶颈后再评估。 |

诊断已有字段限制和容量预算、记录/缓存分区、原生媒体取消等待、临时目录活跃资源保护，以及投屏访问令牌等机制。本轮没有证据要求为这些模块另建一套平行基础设施。

主机工具还有一个低优先级清理项：`cmd/probe/main.go` 的若干错误分支直接 `os.Exit`，会跳过 `main` 已登记的临时目录清理。建议把工作移入返回 error/退出码的 `run` 函数，待清理完成后再退出；该问题属于诊断工具，不冒充移动端临时目录泄漏。

## 设备验收仍应单独完成

优先使用当前发布包完成 [设备清单](ios-device-checklist.md) 中的核心项，记录设备/系统、签名方式、来源/媒体类型、网络与构建：

1. 关闭/开启提前开播分别长时间连播，核对实际画面、声音、换集耗时和退出后内存，而非只看进度前进。
2. 定位、切集、锁屏 5/30 秒、PiP 进出及暂停意图，重复测试迟到事件是否恢复错误播放状态。
3. 后台下载、网络切换、低空间、进程被回收与用户强制关闭分开记录；前台整理与传输完成不可混同。
4. 曾出错的同一电视/蓝莓接收器复测 AirPlay 连播、取消与回手机；Cast/DLNA 分别验收。
5. 小屏/分屏、大字号、VoiceOver 与系统分享面板。页面组件测试不替代真实读屏和系统 UI。

跨站搜索、跨页面投屏、Cast/DLNA 队列可作为后续产品增量，需明确结果身份、请求预算与设备能力；当前可靠性问题具有更高优先级。

## 建议实施顺序

1. **可靠性修复**：F2 下载操作交错、F4 空文件、F5 网络策略；新增针对竞态的受控回归，再运行相关已有套件。
2. **找剧与响应性修复**：F1 真实搜索分页、F3 目录锁/超时；保留补季和缓存数据完整性，补并发/取消/重放测试。
3. **恢复与交互**：R1 启动恢复、R2 启动过渡页、R3 独立重试保存，补失败路径和小窗口测试。
4. **按量测优化**：下载增量更新、隐藏页面展示工作、备份解析与启动清理，先用可比样本确认收益。
5. **再决定结构调整**：依据上述修复及设备数据逐步拆职责；不同时改存储、播放器和全局状态模型。

站源维护可作为独立的小批次，先调查野果/观果的已见失败，再复查其余样本；接口恢复与应用基础层重构各自验证，避免把环境性验证限制混入代码修复。

首批完成标准是用户操作可正确终止下载、无效本地文件可修复、搜索真正增加结果、等待能按时结束。后续性能工作需要分别报告主机结果与设备结果。
