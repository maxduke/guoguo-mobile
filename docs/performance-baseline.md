# 性能与缓存基线

2026-10-09，基于 `bfae6c6` 的代码及本轮查询优化。结果用于选择改动，不能当作手机性能承诺。

## 可复现范围

Flutter 3.47.4 / Dart 3.13.3，Linux x64，AMD Ryzen Embedded R1600，进程可见 2 个逻辑处理器。Flutter 调试测试，每项先预热一次、采样五次，表中为中位数；OS 文件缓存已热，不模拟首次安装或冷存储。完整样本、系统版本和时间见 [优化前](performance/host-before.json) / [优化后](performance/host-after.json)。

合成目录包含标题、长简介、分类、标签、封面地址及 50 部 × 40 集分集缓存。目录资料与当前分类成员各保存一份，采用实际 `CatalogStore.cacheSnapshot` 格式；收藏和历史分别使用同样数量的作品。调用实际 `AppStore` 恢复、`AppFileStorage` 分区原子写入和查询函数。尺寸与负载有意固定，不能推断真实用户的资料量、工作集或站源速度。

```bash
GUOGUO_PERF_OUTPUT=build/performance/current.json \
  flutter test --no-pub --concurrency=1 --reporter=expanded \
  test/performance_baseline_test.dart
```

普通 CI 默认跳过两项测量，不设置易受机器负载影响的毫秒门槛。重测应使用同一硬件、SDK、模式和样本配置；单次或跨环境结果不能直接比较。

## 磁盘、恢复与渲染

以下为优化后测量，写入包含现有快照、脱离可变输入、后台编码、flush 与原子替换；恢复包含文件读取、JSON 解码和业务对象安装。主机环境和 GC/IO 会产生波动，未改动的持久化路径不据这些前后差异宣称性能提升。

| 目录 / 记录 | 缓存文件 bytes | 记录文件 bytes | 记录写入 ms | 缓存写入 ms | 读取及恢复 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1,000 / 100 | 2,629,194 | 263,756 | 8.4 | 83.1 | 56.9 |
| 10,000 / 100 | 24,803,396 | 263,756 | 10.9 | 682.3 | 552.7 |
| 10,000 / 1000 | 24,803,396 | 2,640,476 | 85.2 | 674.2 | 598.0 |

固定 100 条收藏/历史时，目录增至十倍仍写同一个 263,756-byte 记录文件；进度保存不序列化目录/分集缓存，由分区存储回归另外验证。1,000 条长资料的收藏/历史增大了记录文件和写入成本，应纳入设备复测。10,000 部合成目录的缓存约 23.7 MiB，读取/解码/恢复约半秒；这不包括原生核心、网络、首次画面或冷文件读取，不能称为应用启动耗时。

390×844 的实际 `LibraryPage` 在 1,000 和 10,000 项时都只构建 6 个首屏 `DramaCard`；实际 `DownloadsPage` 在 100 / 1,000 条目时都构建 5 张首屏剧卡片。下载样本每剧 10 集、分集收起，省略分片任务和原生恢复。封面显示占位，不访问站源、不计图片下载/解码或真机字体栈；记录的 `pumpWidget` 时间是测试调用耗时，不能当作手机帧耗时。已有观看进度/收藏局部通知回归继续保护目录和应用外壳不被无关事件重建。

JSON 的 RSS 是整个 Flutter 测试进程的当时驻留内存，包含框架、合成数据及先前样本，不能解释为单个缓存堆大小、手机内存或内存改善。

## 0.19.2：减少目录和缓存的重复工作

2026-10-10，基于合并后的 0.19.1（`539cb4b`），沿用上述主机、SDK、合成数据、一次预热和五次采样。新增 `cacheWriteBurst5`：同一轮同步提交五个 `AppStore.persist(records: false)`，等待全部完成，测量整个批次的时间。此次只运行数据操作测量，不追加手机帧或图像指标。完整样本见 [本轮优化前](performance/catalog-work-before.json) / [本轮优化后](performance/catalog-work-after.json)。

```bash
GUOGUO_PERF_OUTPUT=build/performance/cache-burst.json \
  flutter test --no-pub --concurrency=1 --reporter=expanded \
  test/performance_baseline_test.dart \
  --plain-name 'synthetic catalog and partitioned disk baseline'
```

| 目录 / 记录 | 五次同期缓存保存：优化前 ms | 优化后 ms |
| --- | ---: | ---: |
| 1,000 / 100 | 573.4 | 101.4 |
| 10,000 / 100 | 3907.2 | 728.7 |
| 10,000 / 1,000 | 3872.7 | 755.4 |

生产 `AppFileStorage` 只合并尚未开始的目录缓存写入，入队时保留最新快照获取函数，到达写入位置后才生成并脱离输入，再后台编码、flush 和原子替换。同期五次保存只构造和编码一份快照；若首份已经开始，后续请求共享一份等待中的最新快照。网络响应间隔大于写入耗时时仍分别保存，不承诺所有请求都得到表中的收益。单份大缓存仍需原有序列化和写入成本，不能将批次收益解释为所有单次写入变快。

每个等待者只有在覆盖其请求的快照提交后才成功，失败共同报告且可重试。公开 Map 写入仍在调用时脱离输入。容量统计和清理作为队列屏障，关闭此前的合并批次；较晚保存不会被移到屏障之前。收藏、历史、设置及普通 FileStorage 的下载清单继续逐次写入，缓存不占用记录队列，也没有定时 debounce 或未等待的关闭前保存。

剧库页面按列表身份、分类、VIP 和排序条件复用当前派生结果；分类集合也只在输入目录改变时重新收集。实际页面回归通过非可见资料的读取计数确认，网络状态、加载状态和失败通知不会重做整表排序；追加分页、资料更新、分类/排序/VIP 变化、来源切换和替换 AppStore 均正确失效。首次排序仍使用原算法，其时间没有被省略或搬到其它线程。本轮没有新的真机帧耗时结果。

`cache_write_queue_test` 另外覆盖 IO 期间的请求合并、等待到各自提交、输入快照隔离、清理/测量顺序、捕获和原子写入失败、导入回滚、独立记录保存、关闭后完成及普通文件的逐次顺序；`library_projection_test` 保护复用和失效语义。

## 0.19.3：后台读取本地 JSON

2026-10-10，基于 0.19.2（`dd0fb02`）及 FileStorage 后台读取改动，沿用同一主机、SDK 和合成资料。一次预热、五次采样，交替调用旧的界面线程读取逻辑与实际后台 FileStorage，读取相同文件。每次操作用 2 ms 周期定时器记录当前 isolate 的最长回调间隔，计入完成前尚未触发定时器的尾段；结果是主机事件循环响应性样本，不能推断手机帧耗时。原始环境及全部样本见 [读取测量](performance/storage-read.json)。

```bash
GUOGUO_PERF_OUTPUT=build/performance/storage-read.json \
  flutter test --no-pub --concurrency=1 --reporter=expanded \
  test/performance_baseline_test.dart \
  --plain-name 'synthetic file read responsiveness baseline'
```

以下为中位数，单位 ms，只测文件/UTF-8/JSON 读取，排除业务对象恢复、界面构建和网络。

| 目录数量 | 缓存 bytes | 旧读取总耗时 | 后台读取总耗时 | 旧最长回调间隔 | 后台最长回调间隔 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 100 | 417,172 | 14.2 | 15.7 | 12.2 | 3.1 |
| 1,000 | 2,629,194 | 47.8 | 71.6 | 42.9 | 5.2 |
| 10,000 | 24,803,396 | 469.1 | 561.1 | 433.2 | 31.3 |

后台读取减少大文件解码占用当前 isolate 的时间，总耗时在这组样本中增加，未承诺更快完成启动。固定 100 条收藏/历史的记录文件约 258 KiB，全部记录样本也保留在原始报告中；小文件承担一次 isolate 启动的额外成本。后台运行也可能受调度和 GC 影响，不能承诺零暂停。

改动仅在 FileStorage 使用已有 dart:isolate：把路径交给临时 isolate，在其中读取并解码，以 Isolate.run 返回文档，不捕获存储实例、队列或回调。记录、缓存和下载清单的调用与格式保持原样；读取继续只读取已提交文件，未完成的写入仍按原队列提交。记录损坏报错并保留文件，缓存损坏降级，缺文件返回 null。业务对象验证和安装仍在原 isolate；后续依照真机结果决定是否继续处理该部分成本。此做法符合 [Flutter 后台解析指导](https://docs.flutter.dev/cookbook/networking/background-parsing)及 [Isolate.run 的传值约束](https://api.dart.dev/dart-isolate/Isolate/run.html)。

## 当前取舍

| 决策 | 结论与依据 |
| --- | --- |
| SQLite / 按实体持久化 | 保留分区文件与队列。记录写入独立于大目录；先在真实记录量和设备上测主线程暂停、恢复和耐久性，再决定迁移。 |
| 目录查找索引 | 暂不引入。先消除字符串分配；现在尾部查找约 0.3–0.4 ms，列表按需构建。若设备上高频批量查找成为热点，再调整归属与索引。 |
| 目录/分集硬限 | 当前没有额外硬容量限，已测量其增长成本。固定条数会改变离线可见目录和续播分集资料，合成样本不能确定应保留的工作集。保留设置中的安全清理；收集实际工作集后再制定淘汰规则，不能把未测得的预算说成已实现。 |
| 已有缓存预算 | 继续使用搜索的 24 项 / 2 MiB / 20 分钟预算、推荐/榜单的有序缓存预算，以及 600 个封面对象限制；不把完整剧库当作推荐顺序。 |
| 播放器替换 / 第二套提前开播路径 | 保留现有原生播放与兼容回退。主机目录指标不能说明手机首帧、冻结、耗电或接收器兼容性。 |
| 跨页面投屏 / 多协议队列 | 保留当前独立协议会话和单一播放端交接；需要明确产品收益及真实接收器验证。 |
| 多站搜索 / 来源或交换功能删除 | 保留来源隔离及现有入口。暂无实际请求预算、失败分布或使用数据支持这些能力改动和删除。 |
